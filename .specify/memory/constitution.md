# 家計簿ダッシュボード（sunabar × LINE）Constitution

Fintech 講座（Day2〜Day5）のチーム開発で守る原則です。仕様書・計画・タスク・レビューはすべてこの原則に照らして判断します。

## Core Principles

### I. デモファースト・段階的リリース

- 各ユーザーストーリーは単独で動かして見せられる単位で作る。P1 が動いてから P2 に進む。
- 常に「今この瞬間に発表しても成立する状態」を `main` ブランチに保つ。
- 期限（Day5 12:00 コードフリーズ）を超えそうな機能は、途中まで作るのではなく次の優先度ごと切り捨てる。

**理由**: 開発期間は実質 2.5 日。動かないものは発表で評価されない。

### II. 秘密情報をコード・リポジトリに置かない（NON-NEGOTIABLE）

- LINE のチャネルアクセストークン／チャネルシークレット、sunabar のアクセストークン、AWS の認証情報は、ソースコード・コミット・Issue・PR・スクリーンショットに一切含めない。
- ローカルでは `.env`（Git 管理外）、AWS では Lambda の環境変数だけで扱う。`.env.example` にはキー名だけを書く。
- ブラウザ（フロントエンド）に sunabar のトークンを渡さない。sunabar API は必ずバックエンド経由で呼ぶ。
- 講座の配布資料（CONFIDENTIAL 表記のスライド等）をリポジトリに入れない・転記しない。
- 誤ってコミット／共有した場合は、履歴の書き換えより先に**トークンを再発行**する。

**理由**: 銀行 API のトークン漏洩は、サンドボックスでも実運用を想定すれば重大事故。講座資料は外部公開禁止。

### III. 本物の API と自作 API の境界を明確にする

- sunabar の API を最低 1 本は実際に呼ぶ（講座のグランドルール）。
- 「こんな API があったらいいのに」という自作 API（モック）は、専用モジュールに分離し、`contracts/` にインターフェースを文書化する。Day5 の発表対象になるため。
- 画面・レスポンスには、データの出どころ（sunabar / 自作 API）を識別できる情報を持たせる。

**理由**: 発表で「どこまでが実在の銀行 API で、どこからが提案か」を説明できることが評価の核になる。

### IV. シンプルさ優先（YAGNI）

- データベース・認証基盤・状態管理ライブラリなどは、ユーザーストーリーが明確に要求するまで導入しない。
- 依存パッケージは最小限にする。標準機能（`fetch`、Node.js 組み込みテストランナー等）で足りるなら使わない。
- 厳密な本人確認などの実運用レベルの実装は不要（グランドルール）。ただし省略した点は README／発表資料に「本番では必要」と明記する。

**理由**: 短期間・少人数で完成させるため。複雑さは説明コストも増やす。

### V. Docker で再現できる開発環境

- `docker compose up` だけで、誰のマシンでもフロントエンドとバックエンドが同じ条件で起動すること。
- ホストに特定バージョンの Node.js を入れることを前提にしない。バージョンは Docker イメージで固定する。
- 本番（Lambda）の Node.js メジャーバージョンと、Docker イメージのメジャーバージョンを一致させる。

**理由**: チームメンバー間の「自分の環境では動く」を防ぐ。

### VI. レビューを通してから main に入れる

- `main` への直接 push は禁止。すべて Pull Request 経由でマージする。
- マージ前に、チームメンバー 1 名以上のレビューを受け、**AI チューターのレビュー**（PR に `@aitutor-review review` とコメントして依頼）の指摘に対応する。
- 具体的なコミット・Issue・PR のルールはスキル `github-workflow`（`.claude/skills/github-workflow/SKILL.md`）に従う。

**理由**: 短期開発ほど壊れた main の影響が大きい。AI チューターのレビューで、秘密情報の混入や典型的なバグを早期に発見する。

## 技術・セキュリティ制約

- バックエンド: Node.js（AWS Lambda のマネージドランタイムと同じメジャーバージョン）
- フロントエンド: React（Vite）
- LINE 連携: Messaging API（Bot）＋ LIFF
- 公開する HTTP エンドポイントは HTTPS のみ。
- CORS の許可オリジンはフロントエンドの公開 URL に限定する（開発中のみ `localhost` を許可）。
- ログ（CloudWatch 等）にトークン・口座番号全桁を出力しない。

## 開発ワークフロー

1. 仕様変更は `specs/` 配下の spec.md / plan.md を先に更新し、PR で合意してから実装する（Spec Kit のフロー: specify → plan → tasks → implement）。
2. タスクは GitHub Issue で管理し、1 Issue = 1 ブランチ = 1 PR を基本とする。
3. PR には、動作確認の手順と結果（スクリーンショットはトークン等を含まないもの）を書く。
4. 毎日の終わり（17:00）に `main` が動く状態であることを確認する。

## Governance

- 本 Constitution は、チーム内の他のルール・慣習より優先する。
- 改訂は PR で行い、チームメンバー全員の承認を必要とする。改訂時はバージョンを上げ、Sync Impact Report を更新する。
  - MAJOR: 原則の削除・意味の変更 / MINOR: 原則・セクションの追加 / PATCH: 文言の修正
- すべての PR レビューで、本原則への違反がないかを確認する。違反が必要な場合は plan.md の Complexity Tracking に理由を書く。
